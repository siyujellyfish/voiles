# G18／P18 V1-F4｜已核准空迭代與中止後綴的可達呼叫圖（2026-11-08）

> **定位**：V1 正式第一個真程式修正批，不是 V1 全部 F1～F4 完成，也不是 P18.1／P18.2 原項 Passed。依 `AI-build/G18-P18-V0-實證盤點與V1施工輸入-20261108.md` 的 F4（Checker 合法但標量 evaluator `Unsupported`）施工。工作分支從已合併 V0 的 main `794f7e6d024ed1406d06c643351c00306ef54882` 建立，不變更原 Checker、Lexer、語法、BorrowTicket、ResourceId、公開 CLI 或凍結 F00／G6／G17。

## 問題與工程原因

`src/struct_stage/execute_call_scalar.rs` 的 `PrivateScalarReturnExpr::collect_source_calls_in_statements` 在原 Checker 核准全部來源後，仍機械式列舉 `while(false)` 與 `for i in 0..0` 的函式呼叫，再透過 `prepare_function_locals` 將「不可能執行」的 callee 編入必需呼叫閉包。即使其餘程式只呼叫 `good()`，私有標量引擎也會因空迭代裡合法的結構局部函式 `idle()` 未接通而錯誤回報 `Unsupported`。此行為與已核准的 P18.2 真零迭代工作計畫（根本不建立該迴圈的執行任務）不一致。

此前 R01 已對「所有分支確定 Return 之後的不可達最後函式」建立排除，但 V0 精確盤點發現空迭代和無條件 `break`／`continue` 後續語句仍可錯誤污染來源圖。**不能一律只選真的執行分支**：一般動態 if、非空迴圈仍必須對 Checker 核准的所有候選來源編譯安全工作計畫。

## 程式修正

1. 僅從原 Parser `TermKind::Scalar(Boolean(false))`（容許原本合法 Group 包裹）證明 `while` 本體確定不執行；其他動態條件不推測結果。原 Checker 已核准整份來源，零迭代時未走的 callee 不進到 `nested_callees`。
2. 以原 Parser 半開 `for` 來源端點、既存 `syntax_shared::integer_i64` 轉換及已核准 `start >= end` 判斷空範圍。非法或未知來源一律保守保留，不默默跳過。
3. 無條件 `return`、`break`、`continue` 後綴不可能經同一真作用域執行；掃描當前語句序列時到此停止，不推斷一般分支必返回，也不把其它動態控制預判為不可達。
4. 原首個入口函式尋找 `first_source_call_in_statements` 與全部來源閉包 `collect_source_calls_in_statements` 使用相同的零迭代判斷，防止第一個函式候選與真可達圖不一致。原 Checker 的 TypedHIR 與 Runtime 控制計畫仍是必須通過的權威，未執行來源零資源／票據與呼叫事件。

## 四筆真原 Checker→Runtime 正反

- **空 for 正例**：合法結構局部函式 `idle()` 雖存在於 `for i in 0..0`，但只有 `good()` 真進入並返回 7，閉包不含 idle，未走路徑零呼叫。
- **while(false) 正例**：同來源結構局部在已驗證 false 的 while 內不進圖、不 Enter，main 仍真正返回 7。
- **正 for 負例**：`for i in 0..1` 可達同一結構局部，標量 evaluator 仍須 `Unsupported`（不以空迭代的安全推導偷渡尚未接通的 struct 能力）。
- **來源計畫篡改負例**：原已執行的空迭代結果若移除真編譯的必要 callee，`matches_source` 須在任何真執行前 `SourceChanged` 拒絕。

真測試集中在 `struct_stage::g18_private_scalar_call_tests`，不修改 F00 凍結原 P14.1／borrow_safety 測試列表。普通函式專項 Gate **311→315**；原 P18.1／P18.2／P18.5 只新增可追溯候選，不修改正式狀態與原嚴格 `--check`。
