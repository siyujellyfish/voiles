## 一、反覆施工而未結案的可核實原因

1. **驗收條件未封閉**：歷來大量 PR 的「退出條件」是 G18 專項 Gate 從 N 增為 N＋k；正式 `核對G18原六項驗收差距.py` 仍回報 0/6。要改成每批都關閉明確的「原始義務 ID」，並列出尚未關閉的同項義務。
2. **準備器反覆補來源形狀**：普通函式執行器 `src/struct_stage/execute_call_scalar.rs` 約 9,521 行，含 AST 掃描的可達函式閉包、TypedHIR、控制求值、借用與事件核對。#639／#640／#642／#643 的主因是合法來源的呼叫形狀與不可達 HIR，故不應再以個別表面形狀無限加分支；應逐步以已經編譯、由原 Checker 核准的控制工作計畫當唯一可達依據。
3. **安全責任分散**：普通函式、遞迴字串及同步 self 目前由 `execute_call_scalar.rs`、`execute_recursive_str.rs`、`execute_method_self.rs` 分別持有部分執行路徑，僅共享部分 `shared_call_exit.rs` 稽核。#644 揭露內層正常返回錯將父票當整個快照釋放，#645 揭露錯誤退出先還外票再清內層。要逐項共用同一個已核准的退出協定，不直接大爆炸重寫三套引擎。
4. **正式狀態和證據解耦**：R07 的 `--audit` 真重跑只確認各子集案例存在且正確，`--check` 仍需六原項全 Passed。新增證據數不構成將某原項狀態改為 Passed 的權限。
5. **規格確實待決**：D18-01-A～D 遞迴、受控執行預算已核准；D18-02-A～D 同步方法、多載、跨 await 安全原則已核准，但 async 啟動／調度／喚醒／取消／錯誤傳遞的外顯契約尚缺完整裁決。不能把 BlockedByDecision 當成一律永遠拒絕 async 的「完成」。

## 四、CI 與 PR 控制：避免將驗收時間浪費在單一邊界修補

1. **每批施工卡**：「義務 ID→原 Checker 可接受的最短合法來源→實際錯誤／缺口→原碼修復→非法反例→真 Runtime 事件→已存在回歸→尚未結案項」。若不能指出關閉哪條義務，除明確排除阻塞的架構工作外，不單獨開只增加測試數的 PR。
2. **批次大小**：同一安全原因可收斂 2～4 個相關情境於同一 PR；別把不同借用權限假設混成一批。編譯錯誤與新測試先做最小局部驗證，然後在最新 PR HEAD 跑完整 Rust、Gate、原 F00/G6/G17；同一批未完成不要來回合併。
3. **單一權威**：原 Lexer／Parser／Checker／TypedHIR／DeclarationId／BorrowFact 是靜態核准來源；OwnedStr ResourceId 與 BorrowSafety Ticket 是動態責任；shared_call_exit 是事件查核，**不建立新借用**。禁止透過重掃來源文字、按名稱比對、預先求值、偽造 Call／Return／Move／ResourceEvent 取得 PASS。
4. **不動凍結測試清單**：F00、G6、G17 正式證據快照與名稱計數不要改，新增 R 測試集中 G18 專項，避免先前 #644 曾出現的 G3 字串唯一性和 F00 P14.1 來源列表衝突。若 Gate 靠文字匹配而非語意誤報，優先保留原合約及原證據，再修整施工方式。
5. **CI 精確規則**：只有最新 PR HEAD「Rust 前端建置」「Rust 獨立架構測試」「專案檢查」三項均 completed/success、作者／base／mergeable 核對後 Squash merge；合併後必核對最新 main **同一 SHA** 三項 success，再開始下一批。任何失敗先讀對應 job logs、修正新 HEAD 重跑，禁止以舊綠燈覆蓋新紅燈。
6. **狀態變更禁止捷徑**：專項 Gate 從 311 增為任何 N，仍須在真正缺口閉合時才調整狀態；`--audit` 只證明追溯存在；`--check` 持續非零直到所有六原項真的 Passed。不可刪除合法正例、放寬 Checker 或修改要求來讓 Gate 變綠。
