## 三、效能分析：可證明的複雜度與量測方法

### 已確認修正：診斷來源位置

- 舊版 `Source::position(offset)` 對每次呼叫從檔案開頭逐位元組掃描，單次為 **O(offset)**；若輸入長度為 `N` 且多筆錯誤分布在全文、診斷數為 `D`，位置換算最壞接近 **O(N×D)**，`D` 隨 `N` 增長時即可能趨近二次。
- 本批將 `line_starts` 在 `Source::new` 一次建立，額外空間 **O(L)**（`L` 為行數）、建表時間 **O(N)**；每次行欄查找以 `partition_point` 做 **O(log L)**。保留 CRLF 中間位移與 byte column 的原契約。
- 來源單位、記號與 AST 尚各自有配置；大檔案峰值記憶體仍可能是多份資料疊加，不能據此聲稱全前端已變為單趟處理。

### 可重現觀測

`tools/效能基準.py` 使用真正編好的公開 `voiles` 命令，生成各 **128／512／2048** 個合法宣告及獨立非法 UTF-8 位元組兩類檔案，每一規模暖機一次，後續重複七次、列出中位／最小／最大毫秒及輸入位元組。CI 步驟僅作觀測，不因 GitHub 共享 runner 抖動設不可靠的固定毫秒門檻。

執行方式（同 README 的 stable `rustc` 建置後）：

```sh
python3 tools/效能基準.py ./target/p02/voiles --repeat 7 --sizes 128 512 2048
```

此基準**包含程序啟動、單檔 IO、詞彙／靜態流程或錯誤輸出**；不能當作純解析器吞吐量，也不能代表未公開 P13～P16 執行期速度。現行 CI 為預設未最佳化 rustc 建置，數據不可外推至正式發行最佳化後端。正式數字以本次 PR 最新 HEAD CI 測試工作日誌記錄，尚未量到前不可捏造速度提升百分比。

### 尚待實測的風險假設

1. **分支狀態複製**：`flow.rs` if 鏈對 `entry.clone()` 及多條分支 `clone()`；`struct_stage.rs` 亦在條件／迴圈複製作用域。要新增「同樣 AST 節點數、不同深度／分支數」的私有測試比較，才能判斷是可接受常數成本或非線性退化。
2. **結構解析重複查找**：`struct_stage.rs` 在函式／方法、具名欄位與預設求值多次使用 `iter().find()`；大量欄位或參數下可改為預建索引，但先維持目前錯誤順序、原始來源跨度與 VB16-01-A 語意。
3. **建置成本**：Rust CI 的 build 與 test 工作因 BK06 依設計各自編譯核心，test 另編譯 `--test`；現階段應觀察各工作牆鐘時間，再評估快取或分拆測試模組，不能為了效能違反既定相依規格。
