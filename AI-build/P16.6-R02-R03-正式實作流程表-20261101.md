### 0.22 F01／F04 真 Checker 的成員型別來源與安全計畫連接

- `common_ir::VerifiedTypedMember` 的原始責任僅限 `ModeNodeIdentity(Field/Parameter)`、`Name/Type` token、已解析 `TypedDeclaration<String>`，它本身不能建立 BorrowFact、ValueSlot、ResourceId。**該限制是確保來源型別證據不會冒充擁有權的正式邊界。**
- 正式 `Checker::known_type` 取代不同路徑重複測試的基本型別及已存在結構名稱判定；欄位、方法參數、一般函式參數逐筆通過原有 Checker 後，直接以 `record_checked_member` 收集證據。來源角色與名稱、型別 token 由 F01 唯一原 Parser 提供。
- `VerifiedSafetyPlan` 在交付前須證明原 AST 的所有上述成員沒有缺漏或假冒、普通函式參數與真正詞彙 DeclarationId 完全一致，並驗證 `NodeRole`、模式、UTF-8 起迄與 var/const 權限。注記帳簿與可借用者帳簿分隔；不可倒灌另造靜態安全裁決。
- 保持所有 P01／24 P13～P16／113 私有來源／八橋接事件 G0 精確回歸；本批只解決 F01/F04 的型別來源宣告消費，仍須 F02/F03/F04/F05 G1/G2 完整根因簽核。

### 0.21 F02 公私正式 Call 結點的唯一 enum 變體權威

- 公開 `ZeroArgCall(ParsedNamedCall<()>)` 與私有 `Call(ParsedNamedCall<Vec<Term>>)` 原有兩份變體宣告。由 `define_shared_expression_kind!` 生成唯一 `Call(ParsedNamedCall<A>)`，參數型別 `A` 明確受公開 `()`、私有 `Vec<Term>` 核准權限限制，公私 P09/P10/P11/Checker 真正消費相同正式 AST 泛型形狀。
- 不能錯把 P08 原有 `ZeroArgCall` 觀測文字當成正式 Rust enum 的第二份權威；正式 enum 可刪舊變體但外部診斷、位置檢視快照須完全相容。
- 私有零參數 `name()` 仍因 `Struct()` 與普通函式外觀重疊，交由 `Construct` 暫存、Checker 後續消歧。此處仍是 F02 待消除的原始組樹權威；若直接全部改 `Call`，可能改動 P16 受限資源建立與診斷優先序，故未證明前不得刪除。
- 這是 F02 子項，不是 F01～F05 整包驗收；須經 G0 正反精確來源與八橋接 CI，G1/G2 尚未簽核。

### 0.20 F01 私有欄位／參數完整 name/type token 來源契約

- 核對既有 `Field.declaration_span` 只具有整段宣告跨度、`Parameter.declaration_start` 只具有名稱起點；若不在真正 Parser 消耗型別 token 時取得原始來源身分，後續 `TypedDeclaration` 可能仍靠名稱字串宣稱型別。

## 2. 封閉策略與資料權威

- **共同 AST／HIR 只有一套權威產生者**：公私已核准交集直接使用正式共同解析核心；模式限定的語法保留差異節點及明確授權拒絕，不自行放寬 MVP-A。
- **同一引用只有一個解析宣告身分**：來源位元組半開範圍、名稱解析 `DeclarationId`、型別及可達流程邊在正式 HIR 中相互關聯，不再在後續檢查重猜名稱。
- **靜態借用身分與實際票據須區分層次但不可矛盾**：每個可能的 CFG 分支可保存靜態借用身分／條件狀態；只有已證明的可實際化路徑取得或釋放真正 `BorrowTicket`。不可在試探性分支副本內胡亂簽發真實 tracker 序號。
- **安全狀態只有一個可寫入來源**：所有權、部分初始化、借用有效期與資源義務由共同轉移管理；原有不同審核器如保留，僅作檢查或唯讀適配，不能獨立修改權威結果。
- **事件來自真實已執行的已核准路徑**：`VerifiedSafetyPlan` 的存在不等同執行。只有執行期已產生的 UTF-8 事件才能核對清理，不得由靜態分析臆造未執行分支的 Created／Released。
- **不提前 P17**：所有方案只重構目前已核准的公開 MVP-A 與私有 P13～P16 子集；未核准語言能力一律維持保守拒絕。

- 原公開／私有交集差異投影繼續驗證左結合、括號與 UTF-8 位元組跨度；但完整函式、語句與 Typed HIR 仍屬 F02/F03/F04 待驗證，不提前勾選完整工作包。
- 本組變更集中於同一 PR 完整測試與最新 HEAD CI 後 Squash merge，不逐檔合併。

### 第三整合批：F03 條件分支正式節點共用

- 新增 `common_ir::ConditionalBranch<Condition,Body>`，公開 MVP-A `IfChain.branches` 與私有安全 `StmtKind::If.branch` 直接持有同一泛型 AST 資料型別。
- 正式公開名稱／型別／Flow／所有權探針與私有 Lexer→Checker、所有權合流、八條 P16 資源事件橋接都改讀取共同節點的 `condition` 與 `body`。
- 保留公開平面 else-if、私有嵌套 else-if 的可達表示差異，及 `no/otherwise` 既有權限／診斷。不得因共用分支資料形狀而開放 P17。
- 此批統一了一種正式分支結構，**不是**完成全部函式／區塊／宣告解析及 Typed HIR 的 F03／F04 根因結案。

### R03 F09 前置獨立安全整治：單一資源清理與借用票據雙帳簿身分

- 在不更動私有 Checker 活性模型前，將 `SafetyPipeline::record_resource_cleanup` 納入既有雙側預檢後無 `Result::Err` 的 `commit_release_resource_checked`。
- 安全管線簽發真實 `BorrowTicket` 前，先驗證資源責任帳簿也存在相同 `DeclarationId`；分歧時不能留下活躍票據。新增兩表分歧／不存在的資源／重複釋放／不清除別的欄位或所有者的負例。
- 此整治獨立於完整 F08/F09 共用 `SafetyState` 的建立，不以抽象管線已修好就虛構整個 R03 的權威狀態統一。

### 第四整合批：F04 公私正式 Checker 的共同具型別引用契約

- 原公開 P09→P10/P11 的 `ResolvedScalarUse` 擴充為泛型 `common_ir::ResolvedUse<T>`；正式公開 P10 直接消耗已驗證 `DeclarationId+ScalarType`。
- 私有 `Binding::semantic_use` 由真正詞彙綁定建構同一 `ResolvedUse<&str>`，正式 HC14 直接來源存取及借用授權讀取此共同身分而不重新猜測同名變數。私有 `str` 仍遵守原 Copyable／Move／借用限制，不加入公開 `ScalarType`。
- 同一型別化引用外殼已進入兩套正式 Checker；但仍無完整以所有 AST 節點和 CFG 為來源的共用 Typed HIR 權威輸入，不得僅以此批宣告 F04 或 R02 完成。

### 第五整合批：F03 if／else-if 共同正式解析演算法

- `syntax_shared::IfSyntax` 只抽象化入口原有的條件解析／區塊與診斷；`parse_if_chain` **唯一實作** if、else-if、else 的分支順序、換行回退與來源位置。
- 公開 Parser 的 `if_chain` 及私有 Parser 的 `if_statement_kind` 均直接消耗同一解析結果，再依已核准公開平面 `IfChain` 或私有巢狀 `If` 產生既有安全 AST，不能以此擴張 P13/P17。
- 現有共同交集多層 else-if、無 else、分支副作用、UTF-8 診斷和資源清理事件仍須完成最新 HEAD CI。此批只完成控制流程一種正式共用解析演算法，F03 其餘語句／函式文法未結案。

### 第六整合批：F03 正式函式宣告解析順序統一

- 公開 `parser::Parser::function` 與私有 `struct_stage::Parser::function` 改成正式呼叫唯一 `syntax_shared::parse_function_decl`。
- 統一 fn 名稱→左右括號→參數→回傳箭號→回傳型別→函式本體的 AST 來源生成順序，回傳 `ParsedFunction<P,R,B>`；兩入口仍各自核准參數、型別、診斷、原始跨度與所有權。
- 公開保持 P01 零參數、int/bool、最外層明確 return；私有保持原參數、方法及 struct 能力限制，不以共用宣告核心偷渡 P17。
- 本批與已合併共同 if/else-if 核心一樣，均替換實際重複正式解析路徑；其餘 F03 語句／區塊或 F04 完整 Typed HIR 仍需硬性驗收。

## 5. 跨批必要測試與回歸契約

- **公開 P01**：49 份原始 `.voil` 來源及 1 項素材存在性測試（歷史 Rust 50／50），全部維持核准接受／拒絕結果；檢查解析與檢查階段先後、診斷繁體中文文字、類別、排序、UTF-8 一基欄位、原始半開位元組來源、CRLF 與 EOF。
- **私有 P13～P16**：原始 24 個正式驗收項目，包含 `int`／`bool`／`float` Copyable、`str` 非 Copyable、list／dict Undecided、來源移動、共享／獨占衝突、參數及 self 有效期、別名再借用拒絕、巢狀遮蔽與保守拒絕。
- **R02 差異**：只比較兩入口「共同已核准交集」的 AST／HIR 等價；另外獨立驗證公開拒絕私有 struct／move／borrow、私有維持經核准的安全子集與公開頂層綁定差異。
- **R03 安全負例**：非法複製、來源已移動、非法歸還／假票據／重複釋放、借用衝突、各種分支合流及 for／while 零次與反向邊、參數逃逸、欄位未初始化或失敗覆寫，拒絕不得污染其他狀態。
- **P16 八條橋接**：逐筆檢查 `ResourceEvent` 中 Created／Moved／Returned／Released 的資源身分、各事件順序、實際清理唯一性、部分建構失敗回滾與最終零洩漏；不可只檢查事件總數相同。
- **效能**：延續 R04 的規模化 if／for 來源，紀錄同環境對照；不預設憑不同 GitHub runner 的數字宣告加速倍率，也不以效能通過代替安全驗收。
- **CI**：每批最新 PR HEAD 均查核 `文件與工作紀錄`、`Rust 前端建置`、`Rust 獨立架構測試` 為 `completed/success`，核對 GitHub 身分、mergeable、Squash merge；有程式碼變更必須同步更新 AI-build。

## 6. 執行與止損規則

1. **F00→F05 優先封閉 R02**，F01 完成後可平行準備 F06 的資料契約，但不可同時對兩套 Parser 與安全 Checker 做大規模未經隔離的修改。
2. **F06→F12 再逐步封閉 R03**；F07 的確定有效期須使用 F04 已解析引用，F10 的 CFG 必須使用 F09 經驗證轉移，F11 計畫才可成為 F12 資源橋接輸入。
3. 任何批次若引起既有公開診斷或私有安全接受集合變化，先比對已核准條款；無充分證據就回退該變更或保守拒絕，不靠修改測試期待值取得假綠燈。
4. 如果出現未經核准的語法、型別、安全有效期或 P17 執行語意，停止該項擴張並在 AI-build 標為待確認；其他相容的工程仍可獨立繼續。
5. **禁止以累積 PR 數代替完成度**。F05、F12、F13、F14 的具體根因證據全部齊備後，才可變更 R02／R03 的正式狀態。
