# G18／P18.5-T4／V7-A2：已暫停取消工作的退休雙帳防偽（2026-11-14）

## 已驗收基線與真缺口

從已 Squash merge 的 PR #779、主線 `2f525981babac8d6213364e3584d6eb887825156` 同 SHA「文件與工作紀錄」「Rust 前端建置」「Rust 獨立架構測試」三必要 CI 全部 completed/success 接續。原 V7 E1～E5 決策保持：直接 `await` 的延遲啟動、單執行緒協作佇列、只在安全點取消、既有 RuntimeFailure、VB15-01-A 跨 `await` 有效借用禁止。

原 `PrivateScalarCooperativeQueue::retire_terminal` 對 `Cancelled` 工作只要求沒有未完成 checkpoint、待執行 token 與不平衡的 `OwnedStr ResourceId` 事件。由於 **`Cancelled(None)` 是合法的「從未開始」取消**，但 **`Cancelled(Some(PrivateScalarGraphCancellation))` 是已經執行至真 await 後逐框架取消的唯一合法結果**，舊守門未核對 FIFO `drive_order` 是否真的抵達 Suspended，亦未在退休時重新檢查取消的 `FunctionEntered／UnwindStarted／FunctionExited／BorrowTicket` 完整因果順序。

因此即使已真執行、生成 P16 資源的工作遭篡改為沒有取消證據，或者只刪除 `UnwindStarted` 卻保留 `Created／Released` 相等，舊退休器都可能錯把工作當安全終態移出 `jobs`。同理，若某工作偽造 Succeeded 狀態並攜帶別的工作完整真結果，舊退休只查單份 `Outcome` 內部平衡，未核對該工作 ID 自己是否真的由 `drive_one` 完成。

## 修正：FIFO 歷史 × 原 R05 整份退出 × 真 P16 ResourceId

- `retire_terminal` 首先讀取自身**不可重複使用的 FIFO 工作 ID** 在 `drive_order` 中最後一次真正 `PrivateScalarGraphPoll`，及 `cancellation_order` 中取消紀錄次數。這些事件仍只由既有 `drive_one／cancel` 記錄；不得用相同結果值、來源名稱或目前狀態文字冒充另一工作身分。
- `Succeeded／Failed` 的正常退休必須確有該**同一 ID** 最後一次 `Completed`，且沒有任何取消紀錄，然後維持原 `Outcome::has_balanced_frame_trace`、P16 `event_trace_balanced` 與狀態／真結果一致性檢查。
- `Cancelled` 必須在 FIFO `cancellation_order` **恰好出現一次**，並只有兩條合法證據組合：**沒有任何 drive 歷史 + `cancellation=None`**（Prepared 零事件取消），或 **最後一次 drive=Suspended + `cancellation=Some(evidence)`**（真正已執行的安全點取消）。
- 對已真 Suspended 的 `Some(evidence)`，將已存在的唯一取消清理結果重建為唯讀 `PrivateScalarCallOutcome { result: Err(StateMismatch), events: 原證據事件, resource_events: 原 P16 事件, parameter_slots_after_exit:0 }`，復用原 `has_balanced_frame_trace` 進行**整份 R05／HC14／P16 綁定及退出一致性稽核**，再維持獨立 ResourceId 事件平衡。這與真 `PrivateScalarGraphContinuation::cancel_suspended` 已使用的同一既有稽核一致，不創造新的 RuntimeFailure、語言層取消結果或 Borrow 權限。
- 任何一項拒絕都必須在 `jobs.remove` 前發生，工作 ID、剩餘結果、FIFO 與真資源證據保持不動；不在 Drop 時默默遺棄資源，不讓已完成錯誤假冒成功。
- `await` 的原 Parser／Checker、E1 無背景工作、E2 單執行緒、E3 安全點、E4 原錯誤、E5 VB15-01-A 與非 Copyable P16／HC14 既有語意**全部不變**。
