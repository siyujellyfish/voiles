## 批次與核對紀律

第一批只做無行為的測試抽離：`src/struct_stage.rs` 的原 `#[cfg(test)] mod` 群組移到 `src/struct_stage/tests_ownership.rs`、`tests_lifetime_resources.rs`，於原層使用 `include!` 引入而非巢狀 `mod`；保留 `struct_stage::舊模組::舊測試` 的識別路徑，避免 `tools/核對-P13-驗收證據.sh` 等依測試名稱過濾的檢查失效。私有 `inspect` 與公開 `check_file` 無變化。

每批在最新 HEAD 的 GitHub 三項必要 CI `completed/success` 且 mergeable 後 Squash merge。不能把新的整治項目冒稱原本 24 個語意條文；也不能因總測試數相同就認定所有安全行為已被新設計覆蓋。

## 第二批（R04／R06）實作設計（#267 最新 HEAD CI 已通過）

- `flow.rs` 使用 `Rc<HashMap<...>>` 實作詞彙作用域寫入時複製；分支 `clone` 不再直接複製每層全部變數，`Rc::make_mut` 僅在受影響作用域寫入或合流時複製該層。新測試檢查共用指標、原來源未被修改、遮蔽與分支負例仍拒絕。此為 MVP-A 確定初始化層，不宣稱私有 P15 迴圈已同步優化。
- 人工驗收腳本在**預設手動執行**保持全部獨立編譯；CI 可設 `VOILES_REUSE_CI_ARTIFACTS=1`，在**同一 test 工作**使用先前已自己重編的 rlib、CLI、Rust --test 執行檔。從另一個 CI job 重用 binary 仍未允許，BK06 不變。
- 官方 GitHub `actions/checkout@v7.0.1` 取代 v4；生成 P01 測試只對固定核准驗收名稱局部 `allow(non_snake_case)`，Rust stable 依編譯器棄用警告改 `AtomicU64::try_update`。無原始診斷／權限語意變更。
- 兩個檔案的功能變更與 CI 工程變更須實際跑舊的全部 P01／P13～P16 安全來源並確認其測試名稱未動，才可標記本批通過。

## 第三批（R01）原始碼責任拆分

在 #266 保留所有測試識別名稱後，將原 `struct_stage.rs` 內部 `Parser` 實作、`Checker` 語意檢查與 `#[cfg(test)]` 真實 UTF-8 資源橋接拆為 `src/struct_stage/syntax.rs`、`safety_checker.rs`、`resource_trace.rs`。入口仍保存原 AST 型別、`Binding`／`LoanBinding`／`FlowState`／`Scopes`，以同層 `include!` 完全保持可見性與測試名稱；避免同一批同時改安全演算法和語言語法。後續 R02/R03 將以此作為開始正式共用解析原語與靜態契約的界線；**這批僅拆檔，不宣稱不同 AST 已統一**。

## 第四批（R02）共通解析基礎，仍保留明確的公開／私有入口

新增 `src/syntax_shared.rs`，供公開 MVP-A 與私有 `struct_stage/syntax.rs` 同時使用 `keyword`／`symbol`／`newline`／`end` 的 token 判斷；同時讓 MVP-A 型別檢查與私有 Parser 使用同一 `integer_i64` 的進位、底線、範圍規則，且公開診斷文字保持原樣。共通測試新增整數正反邊界與詞彙終點對齊。P13 私有語法仍不得對外開放。

此批**沒有**將不同 AST 或函式／struct 文法完全合併；公開的 `parser::parse` 仍只允許 P01，私有的 `struct_stage::inspect` 仍保守拒絕尚未能證明安全的完整語言來源。完整 R02 必須在 P17 入口方案確認之後有共同 AST 或內部 IR 與來源範圍的跨模式正反一致性證據，不可以「共用幾個 helper」偽稱全部完成。

## 第五批（R05）私有名稱定義索引

- 每個已核准 StructDecl 於 Parser 完成、經欄位／方法同層重複名稱拒絕後，保存 `field_index`／`method_index`；`fields`／`methods` 的 `Vec` 原順序不改，VB16 求值及清理不能使用 HashMap 迭代順序。
- Checker 對所有已確認唯一的函式名稱建立 `function_index`，`find_function` 不再每次線性掃描；函式參數及型別／控制流程驗證方式不變。建立索引僅在每次私有 Checker 實例建立時進行，不把來源身分跨檔共享。
- 加入 96 個欄位與 24 個方法查找／順序測試及重複欄位拒絕反例；新模組和舊矩陣必須通過最新 HEAD 三項 CI，才能標記正式通過。
- 本批消除 Checker 的相關熱點查找，**不宣稱整個解析或執行器都變成 O(1)，亦不保證 HashMap 最壞時間複雜度**。待完成實際欄位數 scaling 基準方能評估速度改善幅度。

## 第六批（R03）單一已驗證來源事實與資源前置門檻

建立 `VerifiedPrivateSource`，在唯一 `verify_source_with_ability` 路徑依序完成 UTF-8、詞彙、私有 Parser、完整 Checker（Copyable／移動／借用／生命週期）檢查，再交付 `Source`、`StructDecl` 與 `Function` AST。原本八個真實 P16 UTF-8 資源來源追蹤分別重複檢查，現全部消耗同一已驗證來源；靜態 `inspect_with_ability` 也由同一入口判定。測試比較安全正例與非 Copyable 隱含複製負例的完整診斷一致性及原始位置。

**安全界線**：這是對齊靜態證明與資源橋接的不可繞過前置檢查，不把模擬器合併成可執行 P17 的通用執行期，也不將 `BorrowSafety`、`ValueSlot`、`ResourceEvent` 強行縮成一個不具證明的新狀態型別。完整 R03 還必須在後續一般執行器 IR 將其持有者轉移／借用票據／資源清理一致性持續驗證，現階段不得視為全部完成。

## 第七批（R04）私有分支／迴圈環境寫入時複製

由原 `Scopes = Vec<HashMap<String, Binding>>` 改為 `Vec<Rc<HashMap<String, Binding>>>`，以 `Rc::make_mut` 在實際修改單一作用域時才進行 clone。來源身分、`Binding`／`LoanBinding`／`ValueSlot` 的安全欄位完全保留，`if` 與 `for`／`while` 仍依原本可達路徑及反向邊保守合流，不引入新合法來源。增加私有快照共享、移動後來源讀取獨立與迴圈正反案例；不得在 Rust CI 通過之前聲稱沒有狀態污染。此批降低 clone 快照的重複資料成本，但下游尚有 AST／後繼語句清單的 `clone()`，不可宣稱所有分支建構已完成效能最佳化。

## 第八批（R04／R06）真實負載擴展與過時狀態整理

- 在同一份 `src/struct_stage/perf_bench.rs` 測試中產生 **if／for** 兩類私有安全來源，變數數量及控制結構數量三段增加（8／8、32／24、96／48），分別呼叫正式私有 `inspect`，包括 Rust 前端 Lexer、Parser、型別／借用安全 Checker。
- CI 於既有 test job 已編譯的 Rust --test 執行檔執行 5 次中位數觀測（首次暖機不算），印出樣本來源位元組、資料量、微秒時間、Debug Rust 編譯環境。**非隔離 CPU microbenchmark，無嚴格時間門檻；不同 runner 不可做純演算法加速宣稱。**
- 若負載揭露超線性成本，只可提出有實際數據支持的後續優化，不能把 `Rc` 複製成本下降直接等同整個 Checker 的實測加速率。
- 保留 R02/R03 尚待完整 IR 統一的真實差距，不因 P16.6-R 局部整治通過而偷改 P17 規格。

## 第九批（R04）按實測瓶頸避免沒有借用時的 COW 複製

基線來自 #273 同一 GitHub 工作（2026-10-30，`rustc --test` 非最佳化，先暖機後 5 次中位數；**無前後因果對照**）：

|---|---:|---:|
| 8／8 | 352 | 235 |
| 32／24 | 2,883 | 1,760 |
| 96／48 | 15,241 | 8,858 |

Code review 確認 `release_last_uses` 在沒有借用或只有函式參數借用時仍無條件呼叫 `Rc::make_mut`，造成每個 CFG 步驟與快照合流中不必要的 HashMap 深複製；新實作先檢查**有效且允許提前歸還**的借用票據，若不存在則直接返回；若只有部分詞彙作用域有此票據，僅讓那些作用域進入寫入時複製，其餘仍更新遮蔽名稱資訊以保持原別名有效期語意。新增測試檢查 96 變數共享快照指標不變、函式參數借用不可被提前歸還、真正 alias 最後使用點仍會被正確歸還且原快照不污染。

基線和後續新 HEAD 由**不同時間的 GitHub runner** 執行，觀測值不能直接作嚴格 A/B 倍率宣稱；正式整治須最新 HEAD 的全部 P13～P16 負例及 P01 來源 CI 通過，並保留不開放公開入口。
