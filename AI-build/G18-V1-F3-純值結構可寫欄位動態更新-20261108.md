# G18／P18 V1-F3：原 Checker 可寫 int 結構欄位真更新與有序退出（2026-11-08）

> 施工起點為主線 `f307c70776d6f0f3ae499418440d03e00f0ba64d`，該 SHA 必要 CI 三項均 completed/success。本批是 V1-F3「已核准可寫結構局部」的真正工程子集，並非 V1 全部或 P18 原六項正式 Passed。

## 原始障礙

原私有 Checker 的 `StmtKind::FieldAssign` 已核准合法 `var` 結構與 `var int` 欄位的更新，P16 `MixedStructRuntime::write_int_field` 亦已能保留真正持有者的最新值；但普通函式 `prepare_function_locals` 和 `compile_early_branch` 都未編譯此來源，合法的 `note.count = note.count + 4` 在真正到達函式前錯被 `Unsupported`。

## 實際施工

1. `checked_copy_struct_int_write` 只在原 Lexer／Parser／Checker 完整同源成功後，核對詞彙 `DeclarationId`、型別、原實例可寫、欄位型別 `int` 且可寫、同一詞彙來源位置與 RHS 原 `TypedHIR`；含 `str` 欄位的結構仍不得被此純值執行器假放行。
2. `AssignCopyStructInt` 工作計畫進入原 `PrivateScalarLocalStep` 與 `PrivateScalarBranchAction`，右值在動態工作堆疊先求值；完整計算成功後再用真 P16 `write_int_field` 更新，絕不提前計算、合成新 ResourceId 或忽略原有 BorrowSafety。
3. 只有更新完成才記 `CopyStructIntFieldAssigned(DeclarationId,field,value)`，事件稽核必須看到當前函式仍存活的結構局部；納入 `shared_call_exit` 同步負責的局部寫入順序。尚未證實的來源或事件偽造維持零執行拒絕。
4. 原已核准外層最終 `return` 契約、F00／G6／G17、公開 CLI 與借用／所有權規則均不更動。

## 同源正反

- 已核准 `note.count=note.count+4` 實際讀到更新後值 7，只有一次欄位寫事件。
- true/false 分支只對真正選中的側寫入，未選分支零事件。
- 已建構且寫入的 callee 其後 int 溢位，必一次 `UnwindStarted` 與真結構離域。
- `const` 結構持有者與 `const` 欄位由原 Checker 拒絕。
- 人工篡改真更新事件中的 `DeclarationId`，聯合事件稽核必拒絕。

G18 專項 Gate 候選 **340→345 項**，P18.1／18.2／18.5 追溯同步更新；原 P18.1～18.6 維持 0/6 Passed。只有最新 PR HEAD 和合併後新 main 同 SHA 三必要 CI success 才算此子批完成。
