1. `main_bool_locals` 只接受經唯一 `verify_source_with_ability` 通過且 `verified.plan.declarations.matches` 的 bool 局部宣告，初始化必為原 `ScalarLiteral::Boolean` 或經原 `private_self_checked_ungrouped_return` 逐層真 Lexer 括號驗證後的 bool 值葉；禁止未證的布林算術、動態呼叫、資源、Borrow／Move。每個局部擁有自己的原 `DeclarationId`，與 main int 值槽分離。
2. 在 `main` 方法實參中，bool 來源可能是原 Lexer true/false，也可能是已真宣告的 `main` bool `Name`；名稱必由**同一內葉精確 Lexer Token**、`known_bool_bindings` 和唯一原 `DeclarationId` 證明。新增 `method_bool_sources` 分別記錄每個 bool 位置是否有來源 DeclId，並繼續由原 Checker 唯一方法簽章把值綁到方法形參 DeclId，不允許 int↔bool 混用。
3. 真 `execute_with_fault` 建立 main 純值 bool 動態槽、查核重複 DeclId，方法實參抵達時若屬具名 bool，必讀同一真 main bool 槽並核對原準備值；所有參數完成後才允許唯一 HC14 self 借票與 `FunctionEntered`。未證的值源不建立借票或事件。main 結束清理 bool 槽；純 bool 不假建 P16 OwnedStr ResourceId。
4. `matches_source` 同時重驗 `method_bool_sources`、`main_bool_locals` 與原 `Self::prepare` 重建後的結果；#826 完整封存 Lexer Token 同一性持續生效。竄改來源 DeclId、局部實際值、混淆方法形參順序或刪除來源清冊必於執行前 `SourceChanged`。

## 首輪核心回歸：保留 E1 延遲工作安全邊界

PR #827 首輪 HEAD `6d14783c7a5e4ceca37f74ee27eede2655268414` 文件與 Rust 前端 success，核心測試 **3020 passed／1 failed**。唯一失敗 `b4_main_bool_async_self已核准直接await來源同值槽與FIFO`：原 Checker 合法 main bool 前置局部 + async self 直接 await，但 `PrivateCheckedDeferredSelfAwaitQueue::prepare` 回報既有 `Unsupported("V7 async self 延遲計畫僅限無前置作用的直接 await")`。

原因不是 bool 值槽或 Checker 的安全錯誤，而是原 V7 E1 延遲 FIFO 明確限制 main 僅建構 owner 並緊接直接 await；該 FIFO 目前**不接通前置 main 局部**，不能因本批加入 bool 值槽就在佇列準備路徑放寬。後續修正原測試（保留為同一十項清冊）為：

1. 原 Checker `PreparedPrivateSelfMethod::prepare` 正常核准，真 `execute` 直接 await 成功執行 bool 值槽與 helper／唯一 self BorrowTicket／SharedCallExit；
2. 同一來源進入 `PrivateCheckedDeferredSelfAwaitQueue::prepare` 必受控 `Unsupported`，零 ID 發行、零 job、零 Ready 歷史及資源事件，佇列結構仍正確；
3. **不修改原 E1/E2/E3/E4/E5 決策或 Queue 安全範圍**，亦不將此前置局部延遲案例偽稱已核准的 async 延遲正例。

首輪失敗不可採計；僅修正後最新 PR HEAD 三必要 CI completed/success 才能合併。原 B4/M3/A1/A2 仍未正式 Closed。
