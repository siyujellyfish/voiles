# 專案規則

## 一、名稱與範圍

- 語言正式名稱：`voiles`（大小寫依此）；儲存庫：`siyujellyfish/voiles`。
- 原先名稱已棄用，對外文件、範例與後續實作皆使用 `voiles`。
- 本專案方向為 Python 式編寫風格、Rust 式記憶體安全、直譯優先、具編譯與單檔封裝能力，最終實現自舉。

## 二、專案文件

- 根目錄 `README.md`：外部使用者、目前能力與使用方式；未實作的能力不可宣稱已提供。
- `AI-build/`：開發助手每次工作的依據，包含當前決策、待確認事項與進度。
- 每次規劃或實作都必須同步**修改更新** `AI-build/` 已有對應文件；避免無目的地新增重複檔案與拉長上下文。
- 更新前先讀取儲存庫現存檔案、目前分支與工作現況，不依賴對話推測儲存庫內容。
- 若文件互相矛盾，停止有關的推測性修改，先釐清；不可擅自重新定義已確立的需求。

## 三、工作分支與整合

- 實作與規劃更新在新建工作分支完成，不直接在 `main` 開發。
- 以合併請求檢視差異，採用 **Squash merge（壓縮合併）** 合入 `main`。
- 不得使用直接合併或重定基底合併作為替代。
- **2026-10-10 已確認 P00.3 嚴格保護方案 A**：GitHub 平台應只允許壓縮合併，停用一般合併及重定基底合併；`main` 的修改必須經合併請求、限制直接推送與強制推送，且必要檢查通過才能合併。禁止未經授權略過保護，必要時應啟用不允許管理員略過的規則。
- **平台設定驗證狀態（2026-10-10）**：`main` 已套用啟用中的嚴格保護規則集 [24833435](https://github.com/siyujellyfish/voiles/rules/24833435)，只允許壓縮合併，無繞過角色且禁止刪除與強制推送。GitHub Actions 已產生成功與預期失敗的真實執行結果；已由具管理權限者將 GitHub Actions 的 `文件與工作紀錄`（整合識別碼 15368）設為強制必要狀態檢查，透過 GitHub Ruleset API 重新查核確實生效；規則集沒有繞過角色。合併前仍須驗證最新提交的檢查成功。
- 若儲存庫完全沒有任何提交，允許一次性的最小初始提交以建立主分支；此例外須向使用者說明。
- 持續整合結果未完成或驗證失敗時，不可宣稱已通過，也不應在未確認必要檢查的情況下合併。

## 四、持續整合與效率

- 工作流程盡可能少依賴外部套件、使用快取或精簡驗證；僅執行目前專案有意義的檢查。
- 現階段只檢查儲存庫文件及管理規範，**不假裝已有直譯器或編譯器測試**。
- 新增程式碼後，依實際語言、測試框架和功能補上對應的單元、整合與安全檢查；相關技術方案須先確認。
- 合併請求若有非 `AI-build/` 的變更，至少須同時更新 `AI-build/`。
- 取消同分支過時工作流程以減少等待；不能為了速度而省略必要驗證。
- 對話中不進行高頻輪詢：可查詢一次當下狀態，仍待執行則如實回報連結與狀態，之後再依實際進度處理。

## 五、禁止推測操作

- 未由使用者確認、也不屬第九節純命名委任或第十節編譯器建議方案委任的方案，只能記為「待確認」，不可自行視為已採用。
- 對技術語意、依賴、目錄結構、發布流程、版本保證、硬體及平台支援等不確定項目，不猜測其現況。
- 需要額外技術選型時，優先檢查第十節委任能否涵蓋；對未涵蓋事項，以及移除資料、修改受保護設定或其他授權不足的操作，仍應先取得明確同意。
- 只根據已查證的儲存庫狀態報告完成與否。

## 六、文字與編碼

- 文件與程式註解使用**繁體中文**。
- 儘量使用中文技術描述；語言語法、程式識別字、路徑、平台名稱及無法避免的專有名詞保留原文。
- 檔案讀寫明確採用 **UTF-8** 編碼。

## 七、相同適用情境沿用已核准規則

- 後續若新項目與既有**已核准**決策的適用對象、先決條件、行為效果、限制及規格版本均一致，應先核對 `main` 及既有規格；確認相容且無衝突時，**直接套用同一規則**，不重新要求使用者選擇相同事項。
- 僅有名稱、語法外觀或型別相似，不足以認定適用範圍一致。未核准的型別／語法、Optional 專用檢查的具體符號與候選取得、其他分支縮限、別名、函式副作用／借用、容器 API、複製／移動、Unicode／UTF-8、所有權及標準函式庫，不得由類推自動補定。
- 遇到不同前提、範圍擴張、既有文件衝突或證據不足，明確標記為「待確認」，維持原有規格，不先實作推測行為。
- 直接沿用時，於必要的規格或工作紀錄引用所依據的既有決策編號及適用前提；若現行文件已完整記載，**不要重複編造決策或無實質內容的改寫**。只要有文件或程式變更，仍須遵守新工作分支、合併請求、最新 HEAD 必要檢查成功及 Squash merge 流程。

## 八、規格決策互動選單

- 後續**未納入第十節建議方案委任的**規格決策，**優先提供可直接點選的獨立 A／B 選項**；每一題附簡短方案差異與適用界線，讓使用者不必自行輸入所有代號。選項應可只選部分項目，未選維持未決，**點選但未提交不算核准**。
- 若目前介面無法顯示或提交互動控制，才提供精簡文字回覆替代，不能假稱已收到點選；提交後仍先核對 `main`、再更新 `AI-build`、必要 CI 成功後 Squash merge。適用前提與已核准規則完全一致時依第七節直接沿用，不重複提問。

## 九、純命名事項由開發助手自行選定（2026-10-25 使用者明確授權）

- 後續**僅涉及名稱選擇**、已確立用途與語意不變的事項，使用者已授權開發助手**直接採用最適合 `voiles` 的清楚、一致名稱，不再逐項要求 A／B 選擇**。例如 Rust 型別、變體、欄位或函式的識別名稱，以及純標示用途的內部檔案名稱；優先遵守既有核准命名、Rust 習慣、voiles 名稱風格、可讀性及避免歧義。
- **不因此改名**任何此前已核准的名稱，也不把先前未選的 A／B 選項冒稱為使用者直接選擇；若採委任選名，應在相關 `AI-build` 規格／工作紀錄註明「依使用者純命名授權由助手選定」及實際名稱。
- **純命名授權本身不涵蓋名稱以外的行為與契約；其後如符合第十節另行明示的編譯器建議方案委任，方能依該授權決定**：語言關鍵字及文法／運算子拼字、公開 API 的模組／可見性或匯出位置選擇、資料型別與欄位內容、錯誤語意、流程／相依關係、CI 執行方式、跨工作產物與目錄結構等，只要有可觀察行為或相容性差異，就不是純命名，不能藉本授權自行裁決。
- 與現行已選規格衝突或用途不明時先核對 `main` 及既有權威文件，保持不明部分待確認；純命名完成後仍須遵守**更新 AI-build → 新分支 → PR → 最新 HEAD 必要 CI completed/success → Squash merge** 的專案工作規則及第七、八節未選項目保持未決原則。

## 十、編譯器後續建議方案委任（2026-10-25 使用者明確授權）

- **授權內容**：使用者明確指示「關於編譯器項目未來全數採用建議項目，唯一確保設計風格與我提供的設計風格一致」。因此，對 voiles 編譯器專案之後提出且**已有具體、可核對的建議方案**，開發助手可直接採納符合此條件的建議，不再逐題要求使用者選 A／B；記錄為「依使用者 2026-10-25 建議方案委任，由助手選定」，不可冒稱使用者逐題選定。
- **最高優先：使用者提供的 voiles 設計風格與已核准契約**。依本專案已確認方向：Python 式簡潔易讀的語言編寫風格、Rust 式記憶體安全目標、直譯優先、後續編譯與單檔封裝、最終自舉；實際具體語法／語意以前述已核准現行規格為準。**不得為遷就 Rust 編譯器、建置工具或助手偏好而偷換 voiles 的表面語法、型別／控制流程／容器／安全語意**，也不得將尚未封閉的安全規則宣稱已完成。
- **適用與次序**：涵蓋編譯器／前端／工具鏈／測試／CI 的後續設計與技術選型，以及相關語言規格候選，前提是對具體推薦逐項核對當時最新 `main`、適用條件、先前核准事項、設計風格和相依關係；若相容，記錄採用的確切方案、理由及尚未決定的邊界。無具體建議之舊未決事項不因本委任一次全部變成已決。
- **衝突處理**：任何推薦若與已核准設計風格、明確使用者規格、安全底線或依賴相衝突，不得自動採用、不得私自修訂既有決策；應提出相容替代建議，無法確認時保留未決並要求使用者處理實質衝突。使用者任何後續具體指示優先於一般推薦委任。
- **開發治理不變**：每次決策或實作更新仍需在新分支同步修改既有 `AI-build`、建立 PR、核對最新 HEAD 必要 `文件與工作紀錄` CI `completed/success`、符合 `main` 保護／可合併條件後才 **Squash merge**。不得省略必要測試、聲稱未完成驗收已完成或擅改保護設定。AR04 原 Phase 相依順序、P01～P03 未驗收的現狀不受本委任變更。
