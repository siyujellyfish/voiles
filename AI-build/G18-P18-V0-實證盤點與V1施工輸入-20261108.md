## V0-0 來源的去重與分類

- 權威來源：`tools/核對G18原六項驗收差距.py` 頂層唯一 `證據`／`狀態` 字面值表，以 Python AST **唯讀**擷取，不調用、覆寫或重建原 Checker；Rust 真來源以 `--list` 核對全名並使用 `--exact` **每項真執行**驗證，非僅匹配名稱。
- 來源基線：原六項共 **859 次跨原項引用**，去重後為 **547 個不同的 Rust 來源名稱**（只是已列入追溯的真測試，不等於所有能力可用）。每個原項目前的證據引用量：`P18.1` 177、`P18.2` 69、`P18.3` 178、`P18.4` 162、`P18.5` 176、`P18.6` 97。重複引用可作多項契約的旁證，但不可虛稱新增獨立正例。

- 依義務去重的 **24 個主要既有 Rust 證據**加 **1 個已證實的合法來源錯拒反例**，由 `tools/核對G18-V0原六項義務來源.py` 在 CI 中逐筆真正執行共 **25 項**。主證據是一個可直接用 `rustc --test` 內部執行器重現的測試入口；不以通過一個入口推論其義務已 Closed。

## V0-2 已實證的三類來源（避免盲修）

### A. 原 Checker 接受且私有執行器拒絕（真正工程缺口）

`F4` 的額外來源 `struct_stage::g18_private_scalar_call_tests::g18_r01_真正可達的結構局部函式仍須保守拒絕` 存在於實際 Rust 測試檔 `src/struct_stage/execute_call_scalar.rs`。該測試明確要求 `PreparedPrivateScalarCall::prepare(src)` 回傳 `Unsupported`（而不是 `Check`），因此可辨識為**原 Checker 接受、受限標量 evaluator 尚未接通**的已知案例。可從既有測試重現的 voiles 原始來源如下：

```voiles
struct Archive{
var count:int = 7
}
fn idle()->int{
var r:Archive = Archive()
return 99
}
fn good()->int{
return 7
}
fn route(flag:bool)->int{
if(flag){
return good()
}
return idle()
}
fn main()->int{
return route(false)
}
```

預期：原 Parser／Checker 合法；真 `route(false)` 應走到 `idle()`，但**現有受限標量執行器**不支援結構局部建構而回報 `Unsupported`。V1 必須先核對該路徑是否屬原 P17 已核准執行模型、所需結構持有者及 typed HIR 如何交給共通工作計畫，再處理其可達執行；不得把 `Unsupported` 直接當作非法語法，也不得為了讓測試綠燈放寬 Checker。V1 合法正例還需與 `route(true)` 未走到 `idle()` 的零事件反例成對驗收。這屬實際已存在的缺口，不是憑測試名稱猜測。

### B. 原 Checker 拒絕（不得當作 Runtime 缺功能）

`B5` 以 `g18_r06_原_checker_VB14_借用別名缺乏重借證明不得進真子呼叫` 錨定：VB14 未證安全的借用別名重借由原 Checker 拒絕，不能為了關閉 P18.4 修改語言安全規則。後續只在原已核准的合法身分／生命期內補足正向來源與多框架退出，未核准的動態權限仍維持拒絕。

### C. 已核准 Runtime 子集成功但完整契約未結案

`F1` 前向兩層呼叫、`C3` for-continue Move／Borrow、`R4` 真內層失敗先還內票再還外票、`M2` 同步獨占 self 寫欄位等，都已有可直接執行的 Rust 正反入口。要關閉整條義務，後續批次還要逐原契約補同類合法來源的其他分支、失敗點及跨元件共同責任；不能只累加測試項數。不同執行器各自通過的 R06 案例亦不能冒充一個已整合的共通函式／同步方法 CFG。

### D. 真正需要使用者決策，不能以拒絕代替完成

`A1`、`A2` 尚無已核准真正 async 正例：前者缺 D18-02-E1／E2 的任務建立、await 排程／喚醒，後者缺 E3／E4／E5 的取消點、錯誤傳遞與跨 await 資源退出細則。已有 VB15-01-A 的有效借用跨 await 保守拒絕仍生效；該拒絕**不是 P18.6 async 正向驗收**。決策前同步 V1～V6、V8 已核准部分照常推進。

## 2026-11-09 V1／F4 施工更新：原 V0 已證錯拒的修復來源

本文件上方 `V0-2/A` 是 **2026-11-08 盤點時點的真歷史重現**，不可將已修復的 Runtime 現況倒寫為當時沒有缺口。新批在原 `checked_copy_struct` 僅擴張「原 Checker 真核准、帶已知字串預設的 var str」至既存 P16 `SharedLedger`。原 `route(false) → idle()` 合法來源現在須通過動態執行，得到 `99`，只生成一個真正 `ResourceId` 的 `Created→Released`；`route(true)` 只選擇 `good()`，未走 idle 不得產生任何資源事件。V0 的機讀 `proven_gap` 改註 **HistoricalCheckerAcceptedRuntimeUnsupported → ResolvedInV1DefaultVarStr**，保留相同 source/test 身分的前後因果證據。
