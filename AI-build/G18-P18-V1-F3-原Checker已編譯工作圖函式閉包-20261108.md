## 問題

原 `PreparedPrivateScalarCall::prepare` 雖已有 `prepare_function_locals`、`PrivateScalarReturnExpr`、`PrivateScalarLocalStep` 及 `PrivateScalarBranchAction` 等直接由正式 Checker／TypedHIR 核准的呼叫工作計畫，在建立子函式圖時，仍**再次掃描原 Parser AST** 枚舉所有可能子呼叫；遇到已證不可達尾端還需特例判斷沒有 `int Expression HIR`，並重算 `Unreachable`。此第二套可達性來源與真執行計畫容易分歧；#648 剛為靜態空迭代單獨修正掃描，但不應再不斷替原 AST 加更多「如果」分支。

## 真程式修復

- 第一層 `main` 的原 Lexer／Parser／Checker 候選呼叫入口維持原契約，不提前開啟公開 CLI／bool 函式等尚未接通的語意。
- 從第一個已核准普通函式向下，**直接從相同 `prepare_function_locals` 得出的真正 `return_expr.collect_calls` 與 `local_steps[*].collect_calls`** 建立遞迴呼叫依賴。所有可達函式仍檢查原始宣告型別（目前 `int` 回傳、int/bool/str 參數）及原 Checker 編譯成功。
- 靜態無法執行的 `for 0..0`、`while(false)` 由已有真控制工作計畫不建立工作；全部 if 分支提前 Return 之後原 Checker 未產生 HIR 的尾端亦由 `Unreachable` 工作計畫排除，無須從原始 AST 重新推測不可達的身分。
- 一般未確定的條件分支仍同時收錄兩側可能子函式，**只在真動態選中的分支進入框架**；來源／編譯計畫發生修改，仍由 `matches_source` 的 fresh Checker／計畫全資料比對拒絕。
- 原 `nested_callees` 仍保持正式 Parser 函式宣告順序，以完整原 Checker 的 Parameter DeclarationId／TypedMember 接通每個目標；無來源的呼叫仍由 graph 交接守門拒絕，不偷略過。
