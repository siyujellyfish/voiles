# P21-A｜Unix 實體來源 inode 與硬連結別名守衛（2026-11-05）

> 非公開 P21-A 驗證基礎，延續 [七項原來源登錄](P21-A-多檔來源身分與驗證預檢-20261105.md)。施工基準 `main 3c46fca7519c29381ca16dfe4f2cecfab2beaad1`（PR #519 已 Squash merge）；**P21/G21、P19/G19、P20/G20 均未正式驗收**。

原第一批已核准的內部檔案登錄使用 canonical 路徑防止 `./`／symlink 同檔別名，但 Unix 的**硬連結**可能指向同一實體 inode，canonical 路徑卻不同；同路徑檔案亦可在檢查後被另一個**內容完全相同**的物理檔案原子取代。這兩者都不應沿用舊驗證授權。

## 本批新增

- 以 Unix `std::os::unix::fs::MetadataExt` 取得實際 `(device, inode)`，和 canonical 路徑一起保存為來源身分；同 inode 即使原請求 path 不同也拒絕 `DuplicateSource`。
- `VerifiedSourceRegistry::check_unchanged` 同時核對**原請求 path → canonical、device/inode 與完整原始位元組**。重命名覆寫後即使內容一樣，仍回報 `SourceChanged`。
- 所有檔案初次正式 Lexer／Parser／Names／Type／Flow Checker 之後再次核對一次登錄快照，避免前面檔案在後續檢查期間被直接替換卻提交半舊狀態。
- 非 Unix 平台維持既有 canonical＋原始位元組守衛，**不推測**其他平台的物理身分機制。檔案身分核對是目前可用的前後快照防護，**不是跨 OS 原子鎖檔／並行檔案修改的語言規格**。

## 新增兩項真 Rust 安全負例

| 真實 OS 行為 | 必需回報 |
|---|---|
| `std::fs::hard_link` 建立不同正規路徑但同 dev/inode | `DuplicateSource`，不可登錄兩份權威 |
| 兩份已建立、位元組完全相同的檔案，以 Unix `rename` 原子覆寫來源路徑 | `SourceChanged`，不沿用舊 Checker |
