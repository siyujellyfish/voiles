## 源頭及已批准能力的實際錯拒

基線 `main 9606d571f57b896a5bc536829912d6efd23b2a9e`，同 SHA 三必要 CI completed/success。原 Checker `safety_checker.rs::method_writes` 已能逐項核准 `self.count = n`：`n:int` 為原方法 Copyable 形參，目標是原 mutable int 欄位，所有權與 VB14/HC14 均證明必須以 ExclusiveWrite self 進入。但受限方法執行器的第一句 `FieldAssign` 只接受原 Lexer int **常值**，在 `PreparedPrivateSelfMethod::prepare` 對這個已核准真來源返回 Unsupported，造成 M2 原共享／獨占 self 及 B4 方法參數工作圖未能完整正向執行。

## 唯一來源與動態變化

只修改 `src/struct_stage/execute_method_self.rs` 的**既有首句直接 self.int 欄位賦值**子集，不放行分支內尚未完成的其他寫入形狀。保留原 `write_value: Option<i64>` 的 Lexer 字面值快路，另外封存 `write_parameter: Option<DeclarationId>`。來源在原 AST 必須是 `TermKind::Name`，且精確對應原 Parser 方法 `int` 形參、原 Checker `VerifiedTypedMember(Parameter)` 與 `verified.plan.members` 型別權威（已在方法形參繫結階段逐項查證）、已綁定的真方法 int 引數以及原 Lexer Name token 起訖座標；任意同名 main 局部、bool、未存在形參、其他借用別名都不得冒充。

`matches_source` 連同原 `VerifiedPrivateSource` 防偽重新驗證 `write_parameter` 與既有完整方法計畫，不能事後改寫 DeclId。只有原方法所有參數從真 Caller 求值、Binder 完成，已取得並核對唯一 `BorrowTicket` 且原 Tracker 驗證 `ExclusiveWrite` 之後，才以原方法 `parameter_frame[DeclarationId]` 取得**當次動態 int 值**，交給同一原 `MixedStructRuntime.write_int_field`。沒有另一本可寫所有權帳，不在 prepare 提前寫值，也不新增語法、借用、例外或 async 行為。若來源計畫缺失／竄改，原執行器在任何資源操作前拒絕；入口注入故障維持 `UnwindStarted／LoanReturned／FunctionExited(false)`，絕不假報正常欄位寫入。

## 第一輪 CI 失敗及修正（2026-11-15）

PR 第一版 HEAD `0e485fb5c0b570b14356a4fa73998bb10f672af0` 文件與 Rust 前端建置 success，Rust P04 **2734 passed／7 failed**：七項真動態方法參數寫入均被新增的 `verified.plan.declarations.matches(id, "int", false)` 保守錯拒。回查原 `PreparedPrivateSelfMethod::prepare` 在正式混合方法綁定循環已對**每一份方法參數**建構 `VerifiedTypedMember::checked_private(... NodeRole::Parameter ...)` 並以 `verified.plan.members` 及唯一 `DeclarationId` 核對，而 `verified.plan.declarations` 是另一種（局部／區塊宣告）權威，不應要求方法形參重複登錄於該表。修正**只移除這條錯誤的平行表限制**，保留：原 Checker 全程核准、原 Parameter 成員型別驗證、已綁定的同一 `DeclarationId`、Lexer Name 精確 token 身分、真正 ExclusiveWrite BorrowTicket 及執行期值槽。任何後續測試仍須在 PR 最新 HEAD 全量 CI 成功後才採計，不以首輪失敗冒充驗收。

## 第二輪 CI 失敗與正式受限 AST 路徑補接

修正形參 Member 權威後，第二輪 HEAD `bcd3eb99be4756ea50c0aefa5737ecded0152659` Rust P04 仍 **2734 passed／7 failed**，訊息已變更為 `Unsupported("方法僅接通純 int 區域宣告、後續直線更新及返回")`。這次原因不在形參型別，而是既有方法局部計畫編譯循環對 `index==0` 的真正 `FieldAssign` 僅在 `write_value.is_some()`（字面值寫入）或方法分支存在時略過，未同步辨識新 `write_parameter.is_some()`。因此先前已完成原 Checker 及欄位身份證明的第一句，仍落入「僅支援方法 int 局部」的錯誤分支。修正該前置條件，**只**讓兩種同源已核准的第一句欄位寫入走原 MixedStructRuntime 真獨占寫入路徑，不允許新增任意局部、控制邊、參數型別、資源或 Borrow 行為。第二輪失敗不採計，必須最新 HEAD 同一套三必要 CI 完全 success 後方可合併。
