# P16.6-R03 F11｜Checker 安全證據完整性閘門（2026-11-01）

> UTF-8。本批把 F11 已實作的宣告、直線移交、具名返回與欄位寫入證據視為一組受限的閉合資料契約；尚非包含 CFG 借用最後使用點的完整 `VerifiedSafetyPlan`。

## 正式實作

- `VerifiedDeclarationFacts::evidence_is_consistent` 在真正 Checker 成功完成全部語意、安全檢查後，才檢查要交付 P16 真實執行期橋接的所有證據是否整體一致。
- 具名整筆移交必須有不同的來源／目的 `DeclarationId`，且兩端均有存在的已驗證宣告與相同型別；不允許只有 AST 的 move 形狀就重新產生目標型別。
- 具名 `return .move()` 證據必須有實際宣告來源，return 運算式原始起點不能早於其宣告來源；無效來源與倒置位置不授權任何跨函式資源返回。
- 結構欄位寫入證據必須有可變的真實 `DeclarationId`，欄位確實存在於已驗證結構型別且本身不是 const；來源語句位置不能早於持有者宣告。保守拒絕憑同名或僅有名稱字串造出的假欄位事件。
- 若以上任何證據不一致，`verify_source_with_ability` 不建立 `VerifiedPrivateSource`，所有 P16 建構、整筆移交、返回、欄位覆寫及資源清理橋接都無從取得安全授權；不變更合法語法、Copyable、借用生命週期及診斷先後順序。
- 增加同一真實 Holder 建構→欄位覆寫→整筆 move、以及 str 具名返回兩組正例；篡改目標型別、自身移交、缺失來源、const 欄位冒充可寫、錯誤 return 位置與虛構來源各自必須整表拒絕。

## 正式驗收界線

- 本批實際消除 Checker 安全證據包的另一項閉合性缺口，但 F07 最後使用點、F08 統一可寫安全狀態、F10 全 CFG、F11 動態票據與資源事件計畫仍需真正合併，F12 八條橋接完整驗收及 F13/F14 尚未完成。
- 最新 PR HEAD 三項必要 CI（專案檢查、Rust 前端建置、Rust 獨立架構測試）須 `completed/success`，核對作者身分、head SHA 與 mergeable 後 Squash merge；P16.6-R 維持 4／6，P17 不提前開放。

## F11／F12 同一執行事件不得被多重證據認領（2026-11-02）

- 原已驗證資源證據表雖能逐筆核對來源型別、UTF-8 位置及欄位權限，但未排除**兩個不同具名來源指向同一個直線移交目標**、**兩個不同來源宣稱相同 return 起點**、**兩個接收者認領同一筆欄位寫入語句**。每一筆個別看似合法，合起來卻不能代表同一條安全執行路徑。
- `evidence_is_consistent` 現額外要求移交目標 DeclarationId、return 原始位置、欄位寫入語句位置分別唯一；不同事件仍可重複使用合法來源（不擅自禁止已核准重新初始化／再次移動）。三項證據查詢 `verified_direct_move`、`verified_named_return`、`verified_field_write` 亦拒絕有競爭來源的完整表，不能只拿一筆無衝突外觀的證據繞過閘門。
- 回歸以真正 Checker 成功的 `Holder` 結構移交、欄位覆寫及具名 `str` 返回為基準，注入同型別但不同 DeclarationId 的碰撞來源，證明整表與單筆取證都拒絕，同時保持既有合法事件與診斷不變。
- 只封閉 F11/F12 靜態單一事件認領契約；不意味動態 ResourceId 唯一性、完整 CFG 路徑事件或借用票據已與 Checker 共用一張安全狀態表。P16.6-R **仍 4／6**，必要 CI 全通過後才可 Squash merge。
