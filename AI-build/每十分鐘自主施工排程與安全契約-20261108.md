# voiles 每十分鐘巡檢與自動推進：排程／施工安全契約（2026-11-08）

## 一、目標與分界

- 每 10 分鐘嘗試巡檢 `siyujellyfish/voiles` 的 `main`、必要 CI、開啟中的 PR、`AI-build` 原始施工契約與正式驗收義務。
- 一旦條件可證安全，AI 代理每輪只施工一個已有核准規格支撐的實際缺口；自動建立單一 PR，完成後等待「最新 PR HEAD 必要三項 CI `completed/success`」，再由獨立合併關卡 `Squash merge`。
- 合併後仍須核查新的 `main` **同一 SHA** 三項 CI 成功，才可開始下一批；禁止以 PR 的成功冒稱主線驗收。
- 不把單項 G18 Gate 測試數增加冒稱原 P18 義務關閉；原六項 `0/6 Passed` 在真正全證據閉合前不得改寫。
- GitHub Actions cron **不是**準點時鐘：`7,17,27,37,47,57 * * * *` 為每十分鐘嘗試排程，實際開始可能延遲／偶有跳過。與 ChatGPT 內建最短每小時排程完全分開。

## 二、施工基準與禁止項

- 永遠從目前 `main` 及最新 `AI-build/G18-P18-契約驅動完整施工與結案流程-20261108.md`、V0 26 義務清冊與相關最近更新的工程證據取施工輸入。
- P18 V1／F1～F4 優先關閉實際可重現缺口，依序 V2、V3…V9，不新增未核准語意；V7 的 async E1～E5 如仍需裁決，標 `BlockedDecision` 並改推其他可獨立工程。
- 保留原 Parser／Checker／TypedHIR 權威、F00／G6／G17 凍結、BorrowTicket／ResourceId 安全邊界及公開 CLI。禁止偽造資料、鬆綁 Gate、以 `--audit` 代替正式 `--check`。
- 可自動改動 `src/`、`tools/`、`tests/` 與 `AI-build/`；**不允許排程代理自行改寫 `.github/workflows/`、密鑰、權限或正式驗收勾選**。
- 所有新增文件、註解使用繁體中文與 UTF-8 編碼。

## 三、每輪狀態機

| 事件 | 條件 | 自動動作 |
|---|---|---|
| `blocked-configuration` | 未設 OpenAI API 金鑰或 GitHub App 安全授權 | 只巡檢、輸出待配置事項，不啟動 AI 代理 |
| `blocked-main-ci` | 最新 main SHA 任一「Rust 前端建置」「Rust 獨立架構測試」「文件與工作紀錄」非 success | 只記錄與定位，不進行下一輪新施工 |
| `blocked-other-pr` | 同範圍仍有待整理的使用者 PR | 暫停新增重疊程式碼，由人或專用 PR 修復流程先處置 |
| `develop` | 最新 main 三必要 CI 同 SHA success、沒有進行中自動 PR 與重疊活躍 PR、設定完整 | AI 代理只處理一個已核准工程缺口，產生受限範圍補丁，開啟 `auto/voiles-p18-progress` PR |
| `pending-auto-pr` | 自動 PR 的最新 HEAD CI 未全數成功，或尚未確認 mergeability | 下輪只巡檢此 PR，不搶開下一批；失敗需單獨修復計畫，絕不虛報成功 |
| `merge` | 自動 PR 來源、base、頭部 SHA、合併安全狀態及必要三項 CI 全部可驗證 | 以獨立 GitHub App 權限 Squash merge；下一輪等待 main 同 SHA 的 CI |

`blocked-other-pr` 目前尤其重要：不能把舊的 #667／#671 與新版 #673 當成彼此獨立的可合併工程；**必須先辨識取代關係、處理新舊衝突**，否則 10 分鐘只會製造競爭修改。本次不擅自關閉或合併它們。

## 四、必要憑證與權限

由儲存庫維護者於 GitHub Repository Settings → Secrets and variables → Actions 設定：

1. `OPENAI_API_KEY`：Codex 代理模型呼叫，需留意 API 額度與費用；不應以一般 ChatGPT 訂閱推斷此額度存在。
2. `VOILES_AUTOMATION_APP_ID` 及 `VOILES_AUTOMATION_APP_PRIVATE_KEY`：專用 GitHub App，僅允許本儲存庫 contents/pull_requests 必要寫入；用於觸發一般 PR CI 及自動 Squash merge。**不可把 App 私鑰提供給 Codex 編碼步驟**。
3. GitHub Actions 需允許工作流程使用，且若用 PR 建立服務需確認相應權限政策。絕不可把憑證提交到 Git。

工作流程採分離的 `inspect → agent → publish` 與 `inspect → merge`，在 agent 的容器只給程式碼唯讀 GitHub 存取，完成檔案補丁後另起工作承載 App 密鑰。未配置時安全地停在巡檢。

## 五、工程產出與驗收

- 巡檢記錄：本輪 `main` SHA、三必要 CI、可行動 PR、未決義務、阻塞原因；不因「沒進度」改動正式狀態。
- 實作 PR：逐項列 `義務 ID → 原 Checker 合法來源 → 實際缺陷 → 最小修復 → 非法反例 → 真執行及資源證據`，以及仍未閉合的內容。
- 每輪嚴格限制一個 patch、一個自動 PR；同排程 concurrency 不取消已執行中的施工，以免重複、互相覆寫。
- 自動合併僅限固定命名且帶機器標記的自動 PR；仍要最新 HEAD 三 CI 成功及無衝突，不用「先前綠燈」。
- 需人工裁決時只標記精確決策與相關安全界線；其他可獨立工作可依契約繼續，但不可偷選語意。

## 六、啟用與目前狀態

- 本 PR 只提交排程實作候選，**尚未在 main 生效**。需要其最新 HEAD 必要 CI 成功後按原專案規則 Squash merge。
- 任何排程是否真的能修改程式，還取決於上述 GitHub Actions Secrets／App 設置；沒有這些設定，僅巡檢、不自動施工。
- 配置後以 `workflow_dispatch` 做一次實際驗證，確認 gate 結果及是否能建立正常觸發 CI 的受限 PR，再採用每 10 分鐘長期運行。
- 人工介入範圍只有規格未決、真正衝突、受損憑證或超預算；不以每個 PR／每個批次都要求人工確認為設計目標。
