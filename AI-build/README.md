## 三、語言風格保持條件

- 使用者已確立：**Python 式易讀簡潔**為編寫風格參考、**Rust 式記憶體安全**為安全設計目標、**直譯優先**，後續編譯與單檔封裝，最終自舉。
- `fn`／`struct`／大括號語句區塊／明確型別與 `var`、`const`、`share`、Unicode 字串與專用型別規則是 **voiles 已核准的自身設計**；Python 式不代表必須使用 Python 縮排文法或全套 Python 運算行為。
- **2026-10-23 新版明確取代此前舊語法草案**，所以不能宣稱跨越兩個版本從未改動；本次稽核**未發現新版設計風格被未授權改成其他語言風格**，但不代表完整語意已封閉或存在可驗證的語言實作。

## 四、目前工程狀態與工作方法

- **P00、P01 首版規格與測試契約已驗收（PR #72）；P02～P30 未驗收**。MVP-A 是單檔 Rust 靜態檢查前端；MVP-B 是按 AR04 原依賴完成安全與直譯器後的可執行編譯成果。
- MVP-A 尚須整合並實際驗收的**五個工作包**：受支援子集／AST、名稱型別／資料流、來源詞彙／診斷安全復原、Rust 核心與 CLI 建置、正反測試與前端 CI。這是**工作包**，不是未決 A／B 次數或完成百分比。
- 每次開始工作先核對 `main`，只直接採納已核准規則或符合第十節委任的**具體相容建議**。有風格／語意衝突即保留未決，不以便利性推定所有權、資源、標準函式庫或 API。
- 所有規劃／實作都在新分支修改既有 `AI-build` 對應文件，PR **最新 HEAD** 必要「文件與工作紀錄」CI `completed/success`、符合分支保護後方可 **Squash merge**，不以文件檢查成功冒充 Rust 編譯器測試通過。
