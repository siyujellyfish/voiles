# G18／P18 V1-F4：原 Checker const str 結構使用唯一資源帳的真執行（2026-11-08）

> 本批起點：主線 `dcba92f8008356fb5afd642ea751b84aba152e4f`，必要三項 CI 同 SHA `completed/success`。此處只驗證 const str 混合結構的**受限安全子集**；V1 的 F1～F4 尚未全部 Closed，原 P18 六項正式 Passed 仍 0/6。

## 原始工程缺口

普通函式可從原 Parser／Checker 真合法來源建構只有 int/bool 欄位的 P16 結構，但對持有真 UTF-8 `str` 欄位的結構仍由準備器返回 `Unsupported`。原先普通 `OwnedStrRuntime` 與 P16 `MixedStructRuntime` 分別編列 `ResourceId`，若直接合併事件或為了讓案例通過而偽造 Created/Released，將破壞唯一所有權與跨框架借用的安全界線。

## 本批的真正安全修正

1. P16 `MixedStructRuntime` 的原 VB16 具名優先、預設次之、求值失敗逆序回收機制只保留**一份** `construct_into` 實作。既有 P16 `construct` 照舊使用內部 ledger；新私有 `construct_with_shared_ledger` 讓一般函式顯式工作堆疊把同一個真正 `OwnedStrRuntime` 交給 P16 真建構，故所有 struct str 欄位與一般 str 都使用單一 `ResourceId` 序列與真 OwnedUtf8 擁有者。
2. 對應 `leave_scope_with_shared_ledger` 在普通函式、巢狀控制、break／continue、正常返回、錯誤回滾中使用**同一帳簿**真正逆序釋放；來源事件完全由真 `OwnedStrRuntime` 讀出，不補寫虛構事件。即使 P16 建構過程中溢位，已建立的字串亦留下真實釋放事件。
3. 本階段保守僅允許原 Checker 已接受、結構內的 `const str` 欄位加 `int／bool` 混合（且其建立種子原 Lexer／Checker 已核准）；`var str` 欄位、巢狀複合資源仍在 Prepare 時 `Unsupported`。因此 V0 歷史負例與原義務清冊都**不修改**。
4. 同一詞彙層混用「一般 str 擁有者」與「含 str 結構擁有者」時，現有兩份局部退出序列尚未能證明跨類別完整 LIFO，動態於新增資源前 `StateMismatch` 拒絕、並清理已建立的舊所有者。不同詞彙層仍按既有真 scope 進退。不能用此受限切片宣稱已完成所有 str 結構所有權。

## 原 Checker→Runtime 六項新增正反

- 單一 `const str`＋int 混合結構：真 `Created(1)`、`Released(1)`，函式返回 7，一次局部建立及離域。
- 兩個結構分別具名字串：真 `Created(1)`／`Created(2)`／`Released(2)`／`Released(1)`，返回 14。
- 結構建立後算術溢位：單一真 `UnwindStarted`，所有既有資源完成真正逆序清理，不冒稱成功 return。
- 未選中的結構函式路徑：零函式 Entered、零資源建構或釋放。
- 兩個不同普通函式的字串結構重入：各自取得不同 `ResourceId`，無跨框架混用。
- 同詞彙層一般 str 與含 str 結構交錯：受限 runtime 在第二個所有者建立前拒絕，先前唯一真資源照常回收，維持來源安全。
