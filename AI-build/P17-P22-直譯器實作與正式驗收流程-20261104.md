## 1. 固定前提、工作邊界與目標

- **AR04-A 原相依不可跳過**：P08／P11／P16 → P17；P12／P17 → P18；P10／P14～P18 → P19；P01／P14～P19 → P20；P12／P18～P20 → P21；P17～P21 → P22。**P23～P26 仍屬後續編譯階段，不在本計畫中**。
- 現行對外 `voiles <單一.voil>` 與 `voiles_core::check_file(&Path)` 僅檢查 P01 MVP-A；P13～P16 的 `struct`／`str`／`move`／`borrow` 只在已核准私有安全子集通過，不能因完成 R02/R03 而直接公開。不得破壞檢查命令既有輸入、輸出、診斷與退出契約。
- P17 的第一個可執行垂直切片**僅用既有 P01 核准的 int／bool、宣告、`+`／`-`、無參數函式、`return` 與 `if`**，先走內部執行測試介面；是否公開命令屬 P22／另行已核准入口決策。私有 P13～P16 runtime 只在合法真 Checker 證明後逐功能接通。
- **不能以 `check_file() == Passed` 一個布林值授權任意 AST 執行**：執行物件須具備同一來源的真 Parser、宣告與名稱身分、型別 HIR、可達性／控制流、所有權／借用／資源安全證據；未證明的路徑在產生任何執行效果前拒絕。
- 靜態 `DeclarationId`／`BorrowFact`／Checker CleanupObligation 與實際 `BorrowTicket`／`ResourceId`／`ResourceEvent` 明確分離。執行器只可對**真正走到的控制邊**執行效果、配置與清理；原 F00 四組凍結（49/30、24/157、113/63、15 路徑／57 事件）及 G6 防護繼續保持。
- `float` decimal64、Optional、容器、Unicode 字素、模組、非同步及新借用能力**即使有設計決策，也不得在缺少對應靜態、執行與資源證據時宣稱可執行**。不重新定義 voiles 的 Python 式易讀、Rust 式安全、直譯優先及已選 `fn`、`struct`、`var`／`const`。

```text

  ↓
```

每一 Phase 可有多個小 PR；**子批通過不等於整個 Phase Passed**。必要決策未封閉時，允許與其無關的批次先行，但相依 Gate 保持 `BlockedByDecision`；不能以保守拒絕替代該 Phase 所有已列必需項目。個別 PR 本身成功僅代表該 PR 新增的內容已經驗證。

## 11. 自動測試矩陣及正式驗收基準

| 層級 | 不可省略的證據 | 簽核要求 |
|---|---|---|
| L0 沿用原語法 | MVP-A 原始 P01 真來源、原診斷、IO/UTF-8/CRLF | 既有 `check_file` 和 CLI 行為不漂移 |
| L1 原安全驗收 | F00 四凍結、原 P13～P16 24 項、G0/A6/G3/G4/G5/G6 | 與最新 HEAD 同 SHA，全通過，不因速度刪除真負例 |
| L2 新靜態→執行鏈 | 來源身分／HIR／CFG／SafetyState／ResourcePlan 驗證失敗及無副作用拒絕 | 每個新增可執行節點皆有真正成功與真正拒絕案例 |
| L3 真語意執行 | 值結果、return、循環邊、每次有／無執行的分支 | 不允許透過 mock AST、文字聲稱或假事件冒充 |
| L4 真資源安全 | Created/Moved/Returned/Released、BorrowTicket、失敗 rollback、逆序清理 | 由 runtime 產生實際事件，無雙重／遺失釋放 |
| L5 對外使用者契約 | P22 CLI、錯參數／路徑／Unicode、輸出結果、退出行為、繁體中文文件 | 乾淨環境可從原始碼真執行；不變更舊契約 |
| L6 跨階段完整驗收 | G17→G22 及 G6，6 Phase 原小項、決策核准引用與差距為空 | 只有最新 `refs/heads/main` 真 push 同 SHA 才 `Passed`；PR 只能 `PassedCandidate` |

**效能政策**：在 P17 建立 evaluator 與原 Checker 交接成本基線，再於 P18 控制流程、P19 字素與 P21 多檔做同環境重現觀測；未核准的速度門檻不構成新硬性接受條件，也不得用不同 runner 的數據證明加速。

## 12. 逐批工作分支、CI、合併節奏

1. 每批自最新 `main` 建新分支，先核對相關規格，再提交該批最小可審查原始碼＋真 Rust 正反測試＋`AI-build` 對應進度。**不要靠修改舊測試期望或凍結來讓 CI 過關**。
2. 每批 PR 必須最新 HEAD「文件與工作紀錄」「Rust 前端建置」「Rust 獨立架構測試」三項 completed/success。新 P17～P22 正式 Gate 作為這兩工作流程內必要驗證，防止空過濾或過時入口；避免重複於 CI 啟動同一批次案例。
3. 合併前查 PR 作者身分、最新 head/base、mergeable，僅採 Squash merge。PR 候選結果不可提前標成主線 Passed。
4. 每個 Phase 結尾由新 `main` push 同 SHA 重跑原 P01/G6 和當期 G17～Gxx，核對原子事件、安全負例與文件，才在 `建構階段.md` 將該 Phase 原始 `Pxx.1～Pxx.n` 真正勾選。
5. 先達到 **G17**（最小真執行），再 **G18**（控制流程）、**G19**（容器／字串／核心函式庫）、**G20**（share）、**G21**（跨檔）、**G22**（使用者 CLI）。僅在六 Gate 主線全過、阻塞決策清零、必要 CI completed/success 之後標記 **P17～P22 正式 6／6、M4 完成**，再另行規劃 P23。

## 13. 立刻可執行的起始批次

**優先從 D00-01 → D00-02 → D00-03 → P17-A → P17-B → P17-E 開始**；這條路徑完全使用已核准的 P01 `int`／`bool`、已完成 R02/R03 共通來源證據與內部執行測試，不依賴新的公開 CLI 選項。接著依序做 P17-C／D／F 並封閉 G17。後續 Phase 每完成一批可繼續下一個相容工作包，不以形式上的 Phase 邊界要求對話中斷；碰到必需的未核准語意才保守暫停該工作包。

**本計畫是後續施工順序與證據契約，不表示已新增任一 P17 直譯器程式碼、P18 函式執行或 P19～P22 新語言功能。**
