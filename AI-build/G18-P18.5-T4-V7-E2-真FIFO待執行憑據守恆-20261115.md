# G18／P18.5-T4／V7-E2：真 FIFO 待執行憑據雙向守恆（2026-11-15）

## 起點與未覆蓋漏洞

基於 `main fb289bea1e39f9b574da33c5b8f594ce57ab4a84` 同 SHA 必要三項 GitHub CI completed/success。先前 #785～#788 對原 Checker 私有 async 任務加入真 `wake` 次數、原 `drive_order` 時序、每次 `submit/wake` 的 FIFO `ready_issues` 簽發先後。但目前 `verify_ready_fifo` **只遍歷 ready 現存元素**，尚無反向證明「每一個仍未被 poll 或取消消耗的合法 token 都在 ready」；將某 Prepared 或已醒來 Suspended 工作 ID 直接從 ready 刪除，其他工作仍可推進，全部刪除甚至 `drive_one()` 直接回 `Ok(None)`。這是 E2 排程器完整性的工程差距，不是新增外顯語法。

## 唯一來源守恆規則

在同一 `verify_ready_fifo` 最後執行反向核對：逐一遍歷仍在 `jobs` 的原工作，依原 `drive_order` 次數與原 `wake_order` 次數推導是否仍有未消耗 token。Prepared 僅當原 poll=0 且 wake=0 須有一張 Submitted；Suspended 僅當 poll≥1，若 wake=poll 則尚有一張 Woken，若 wake+1=poll 則目前尚未 wake、不得有 ready，其餘差值拒絕。Succeeded/Failed/Cancelled 不再持有待驅動 token；Running 不能當作合法入列狀態（但原 E3 shutdown 先保留 Running→WrongState）。由每張仍未消耗 token 最後一次原 `ready_issues` 的位置重建排序，與 `ready` 完整比較，拒絕遺失、憑空新增或重排；已退休者不可重新建立 token，但原歷史仍留供稽核。

此外，`drive_one()` 的空佇列分支也必先執行此唯讀稽核才允許 `Ok(None)`，避免偽造空佇列繞過前方有頭元素時才會執行的守門。拒絕必在任何 `poll`、取消、P16/HC14 借票或資源移交之前；來源未改、E1/E2/E3/E4/E5 已核准內容不變。

## 首輪 Rust 回歸實際失敗及相容修復（2026-11-15）

PR 第一版 HEAD `f201f35453a59039617364f0d032d6ccc880b5f1` 在 Rust P04 **2675 passed、2 failed**（建置成功）。兩項均來自舊測試依賴原先未受約束的非法操作，而非正常合法 E2/E3 行為：

- `t4_pending_完成工作偽造Prepared不能消耗真結果也不可再取消`：原測試先把已完成工作 status 竄改回 Prepared，再呼叫 `submit` 並假設新提交成功。新全域守恆本應拒絕此非法狀態的後續提交；改成先合法提交第二個 Prepared，再將原已完成工作偽造回 Prepared，並明確新增 assert `submit==Engine`，維持 cancel／shutdown 不可借偽狀態接受的原目的。
- `t4_cancel_不同工作成功結果不得移植給未啟動的同源ID退休`：原測試直接 `ready.retain` 移走合法的未啟動工作 token，以求先執行後方已 wake 的工作。現在先驗證此非法刪除會被 `drive_one` 拒絕且零新 poll，再恢復 token，呼叫合法 `cancel(unstarted)` 才能移走該 token；後續將其他真成功結果植入未啟動 ID 仍必因原 FIFO poll／取消來源不符而拒絕假退休。此測試不改語言或原取消安全界線。
