## 1. 驗收權威與支援界線

- G17 依 `AI-build/P17-P22-直譯器實作與正式驗收流程-20261104.md` 的原 P17-A～F 各批施工和 G17 正式門檻驗收，不增刪原始六項，不用單一測試代替所有項目。
- `src/execution.rs` 保留正式 P01 `Source → Lexer → Parser → P09 ResolvedNames → P10 VerifiedScalarHir → P11 Flow/Reachability → P12 Functions` 的已驗證真來源，執行前拒絕 AST/HIR、身分、可達性和來源 bytes 竄改。其函式與分支真求值仍是非公開核准子集。
- P13～P16 私有 `struct_stage` 的合法最小 str／struct／borrow 須先完整通過原私有 Checker、`VerifiedSafetyPlan`，動態使用 `OwnedStrRuntime`／`MixedStructRuntime` 及 `BorrowSafety` 實際分配／釋放 ResourceId、簽發／核對／歸還 BorrowTicket。靜態 BorrowFact 與動態票據不可互相冒充。
- G17 的「退出」限 **內部 evaluator 正常返回與錯誤／來源位置／資源清理契約**；新對外執行 CLI、`main int` 對 OS 退出碼、尚未核准的 P22 指令形式不在此 Gate，不能據此自行授權。
- P18 函式進階控制、遞迴停止政策、方法 self／複雜借用逃逸、P19 容器及 Unicode 字素、P20 share、P21 模組、P22 使用者命令仍由各自相依 Phase 驗收，**不因 G17 6／6 而勾選**。
- 原 F00 四組凍結、G6/F14、公開 P01 檢查與原有診斷、所有原結構／字串／控制／來源安全測試不得為 G17 改弱、重置或繞過。

## 3. CI 簽發方式

1. workflow `.github/workflows/前端建置.yml` 先編譯 `src/lib.rs` Rust 全量測試並真正執行，維持舊 49+／F00／G6 防護；此步若失敗則不允許 G17 通過。
2. 新獨立 `tools/核對G17正式總驗收.py --test-bin target/p02/p04_source_internal` 必先透過 `--list` 逐字核對六項總清單的每個測試確實存在，再針對 P17 真正的 Rust 測試模組**分組重新執行**，要求每個模組至少 1 個案例、`test result: ok`、`0 failed`、`0 ignored`、實際通過數大於零。另單獨執行動態退出與返回事件驗收。既有 G6 仍保留正式總 Gate。
3. 在 PR `pull_request` 事件只輸出 `PassedCandidate`；在 `refs/heads/main` 真推送且 `git rev-parse HEAD` 與 `GITHUB_SHA` 精確相同才輸出 `Passed`。不得以 PR 的 merge ref 或上一 SHA 結果當作新主線。
4. latest main 同 SHA 的「文件與工作紀錄」「Rust 前端建置」「Rust 獨立架構測試」全部 `completed/success`，**且 G17 Gate 實際回報 6／6、Passed**，才將原始 `建構階段.md` 六個 `[ ]` 全部改成 `[x]`，另開結案文件 PR 再走一次相同合併流程。
5. 即使 G17 內部範圍驗收通過，後續任何擴大執行語法或公開 CLI 仍需要各自規格與 CI 正反證據，不得繞過 P18～P22 相依。
