# G18／P18.4-B4：原 Checker 方法 var int 直接 helper 重賦值與故障原子退出（2026-11-13）

## 真缺口與原驗收起點

已合併 `main 40537632341aa8bc4ad8a1c087f2c116da515872`（PR #764），合併後主線同一 SHA 的「Rust 前端建置」「Rust 獨立架構測試」「文件與工作紀錄」全部 completed/success。上一批確立原 Checker 已授權同步零參數、單一返回的純 int helper 常值／加減，以及 main／方法局部初始化時真進退與溢位逐框架退票。

但同步方法的已合法 `var int` 重賦值路徑仍無法直接接通同一 helper：`method_checked_int_locals` 在賦值 RHS 預檢採用 `pure_int(..., false)`，而 `PreparedPrivateSelfMethod::prepare` 在 `method_int_assignments` 只允許完全沒有普通呼叫的純算式，`execute_with_fault` 的賦值求值器亦不識別 `Call`。此批限一個已核准直接 `temp = helper()`，不是一般化表達式中的任意函式呼叫。

## 靜態／動態唯一責任

- 原 `safety_checker.rs::method_checked_int_locals` 的 `StmtKind::Assign` 對 RHS 使用既有 `pure_int(..., true)`，讓唯一直接 `Call(helper, [])` 或原核准無參數名稱進入原 `evaluate` 型別與 DeclarationId 檢核；原 `pure_int(BinaryInt)` 子節點必使用 `false`，故 `temp = 1 + helper()` 仍保守拒絕。左端一定是原 Checker 已初始化且合法可寫 `var int`；const、別名、其他資源及非同步保持拒絕。
- 原 Runtime `method_int_assignments` 僅接受當前原 Checker 的 `PrivateScalarReturnExpr::Call { name, arguments: [], awaited: false }` 且與已核准單一 `method_helper` 精確相同，不能透過名稱或不透明算式另尋呼叫；所有來源與執行計畫在 `matches_source` 再次重編完整對照。
- 方法真值求值次序不變：只在全部已核准局部宣告已真初始化、所有前序重賦值已提交後，才進入 RHS helper。從同一 `PrivateSharedCallExitEvent` 記真 `FunctionEntered`，成功才記 `Returned`、`FunctionExited(true)`、`ordinary_calls_completed`，最後才以同一原 DeclarationId 更新 `parameter_frame`，發出一筆真 `LocalAssigned`。
- 若 helper 真整數溢位：先記唯一 `UnwindStarted` 和 `FunctionExited(false)`，絕不提交失敗 RHS 的 `LocalAssigned`；原 R05 再依逆序清理先前已初始化的所有方法局部、歸還現存 self 唯一 BorrowTicket、退出外層方法。前序合法賦值只能留下已提交前綴，未達賦值不能假補。
- 不建立新 UTF-8 資源事件，無未授權 Move/Borrow、一般函式多載、跨 await 或背景工作。先前 F00/G17/G18 所有原正反保持。
